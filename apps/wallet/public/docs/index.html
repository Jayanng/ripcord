RIPCORD Protocol Documentation

Integrate self-custodial Bitcoin operations across the Tachi and TAURUS ecosystem via deterministic 5-of-7 Taproot vaults, spendable VTXOs, cryptographic inclusion proofs, and sovereign unilateral exits.

RIPCORD is a verification-first custody architecture where every balance and settlement claim names its authoritative cryptographic source. Cooperative transfers offer instant off-chain settlement for a minimal protocol fee (1 sat minimum, no L1 mining fees), while the on-chain Tapscript exit leaf guarantees that users can always reclaim their exact Bitcoin on L1 after the configured timelock expires without third-party permission.

Choose your integration path

  • Self-Custodial Wallet UI: Full-featured self-custodial web application with real-time VTXO payments, proof receipts, and hold-to-confirm exit engine.
  • @ripcord/core SDK: Standalone TypeScript package for key derivation, deterministic vault derivation, and payment commitments.
  • Tachi Consensus RPC: Direct interaction with 5-of-7 quorum validators and live WebSocket indexer streaming.

TAURUS VS. LIGHTNING NETWORK

TAURUS vs. Lightning: Superior UX & Stronger Sovereignty

Tachi and TAURUS vaults deliver a superior user experience compared to the Lightning Network while providing stronger self-custody guarantees: zero channel management, no inbound liquidity bottlenecks, no force-closure penalties, and clean unilateral timelocked exits.

Custody Attribute TAURUS Vaults (Tachi) Lightning Network Custodial Wallets / Rollups
Key Ownership User holds BIP-39 seed (never stored) User holds private node keys Operator holds private keys
Channel Management None. Single vault backs arbitrary VTXOs Manual channel capacity & rebalancing None (centralized ledger)
Inbound Liquidity Not a concept. Receive any amount Requires inbound channel liquidity Unlimited (centralized)
Unilateral Exit Guaranteed via BIP68 timelock (CSV) Force close with dispute penalty None. Dependent on operator
Watchtower Requirement None. Exit leaf requires only user signature Mandatory to prevent old state fraud None (trusted operator)
Receiver Availability Non-interactive; receive without active session Node must remain continuously online Supported via custodial backend

Why TAURUS Proves a Superior Second-Layer Model

The Lightning Network achieved breakthrough speed on Bitcoin, but introduced severe operational friction that pushed millions of users back toward custodial solutions. TAURUS solves these structural flaws at the protocol level:

  • No Inbound Liquidity Deadlocks: On Lightning, a new user cannot receive Bitcoin until they have first spent funds or paid a routing node for an inbound liquidity lease. In TAURUS, Virtual UTXOs (VTXOs) are self-contained credit commitments; any user can receive sats instantly to their user Taproot address with zero pre-existing channels.
  • Elimination of Force-Closure & Toxic State: If a Lightning node loses state synchronization or broadcasts an outdated commitment transaction, justice penalty mechanisms can burn or confiscate their entire channel balance. In TAURUS, off-chain state updates are committed to validator consensus trees; there are no penalty games or toxic states.
  • Deterministic Unilateral Timelock Exit: If live validators go offline or refuse to coordinate, the user does not need to run a complex fee-bumping dispute race. The TAURUS Taproot exit leaf is hardcoded to the user single-key CHECKSIG with an on-chain relative timelock (BIP68 CSV), enabling guaranteed single-transaction recovery directly to Bitcoin L1.

GETTING STARTED

Quick Start Guide

Follow these three core steps to initialize a sovereign identity, bind to an on-chain Taproot vault, and begin transacting.

1. Generate Ephemeral Mnemonic

Generate a 12-word BIP-39 mnemonic. Private keys are derived on your device and are never written to disk or browser storage.

BIP-39 Identity Derivation 
import { deriveIdentity } from '@ripcord/core';

const identity = deriveIdentity(mnemonic, 'regtest', 0);
console.log('User P2TR Address:', identity.userAddress);
console.log('L1 Settlement Address:', identity.l1Address);

2. Query Live Quorum & Derive Vault

Fetch the 5-of-7 validator threshold from the Tachi consensus daemon and construct the deterministic Taproot vault address.

Vault Construction 
import { getQuorumWithCache, createVault } from '@ripcord/core';

const quorum = await getQuorumWithCache('https://rpc-regtest.tachibtc.com');
const vault = await createVault({
  network: 'regtest',
  nodePubkeys: quorum.nodePubkeys,
  csvBlocks: 2,
  userKeyDescriptor: identity.userKeyDescriptor,
  threshold: quorum.threshold,
});
console.log('Vault P2TR Address:', vault.address);

3. Fund & Transact

Fund the vault using the Tachi testnet faucet or Bitcoin RPC. Funding is two steps: send BTC to the vault address, then register the deposit in the wallet after it confirms on L1. Registration is what mints the spendable Virtual UTXOs (VTXOs): before it, the deposit shows under on-chain vaults only.

CRYPTOGRAPHIC PRIMITIVES

Deterministic Taproot Vault Construction

Every RIPCORD vault is an on-chain Bitcoin Taproot (P2TR) output governed by BIP-341 and BIP-342.

To enforce that funds can never be spent via an unknown keypath, the internal key is set to a provably unspendable NUMS point. Any spend MUST reveal a valid script leaf from the Taproot Merkle tree.

Taproot Output (P2TR) │ Internal Key: NUMS Point (Unspendable) │ Tapscript Merkle Root / \ / \ [Leaf A] [Leaf B] Cooperative Path Unilateral Exit Path ──────────────── ──────────────────── 5-of-7 Validator <csv_blocks> OP_CHECKSEQUENCEVERIFY Schnorr Quorum OP_DROP <user_pubkey> CHECKSIG
  • Leaf A (Cooperative Consensus Path): Requires valid Schnorr signatures from at least 5 of the 7 registered Tachi consensus validators. This path coordinates atomic off-chain VTXO minting and batch settlements.
  • Leaf B (Unilateral Exit Path): Requires a valid Schnorr signature from the user's sovereign public key after the relative timelock matures. The real leaf (live-verified from the tapscript inspector) is OP_2 OP_NOP3 OP_DROP <user_xonly_pubkey> OP_CHECKSIG, where OP_NOP3 is OP_CHECKSEQUENCEVERIFY.

ARCHITECTURE

Quorum Discovery & Fingerprinting

RIPCORD queries live consensus validators, computes quorum fingerprints, and prevents rogue validator collusion.

Fetching Consensus Quorum 
import { getQuorumWithCache } from '@ripcord/core';

const quorum = await getQuorumWithCache('https://rpc-regtest.tachibtc.com');
console.log(`Quorum Threshold: ${quorum.threshold} of ${quorum.nodePubkeys.length} validators`);

The quorum fingerprint is a domain-separated cryptographic hash covering the exact sorted public keys and consensus threshold. Any change in validator composition triggers an explicit rotation warning.

CRYPTOGRAPHIC PRIMITIVES

NUMS Unspendable Key

A Nothing-Up-My-Sleeve point ensures that funds locked in a Taproot vault can never be spent via keypath.

The NUMS internal key is derived by hashing a standard generator point such that the discrete logarithm (private key) is mathematically unfeasible to calculate:

BIP-341 NUMS Point 
// Standard BIP-341 unspendable public key point:
const NUMS_INTERNAL_KEY = '50929b74c1a04954b78b4b6035e97a5e078a5a0f28ec96d547bfee9ace803ac0';

// Any spend of this Taproot output MUST reveal a valid script leaf from the Taproot Merkle tree.
// No party (neither user nor validator quorum) can spend via the keypath.

ARCHITECTURE

Tapscript Tree Leaves

Detailed specification of Leaf A (Cooperative 5-of-7 Quorum) and Leaf B (Unilateral Relative Timelock Exit).

Both script leaves are compiled into a binary Tapscript Merkle tree. Leaf A enables atomic off-chain transfers and batch settlements. Leaf B provides the sovereign emergency rip-cord: if validators disappear or censor transactions, the user signs a sweep transaction on L1 after the configured CSV blocks elapse.

VERIFICATION

Inclusion Proofs: HAT and RIP

Cryptographic verification guarantees that off-chain state transitions are authentic and verifiable by anyone.

  • History Authenticity Tree (HAT): A Merkle tree structure maintained by the Tachi daemon that records historical note consumption and balance continuity across rounds.
  • Rollup Inclusion Proof (RIP): A cryptographic proof verifying that a specific payment transaction hash is included in the StateDiff committed to the rollup root.

Which transactions carry which proofs

  • Off-chain transfers: carry the full proof chain: HAT commitment, Verkle state-diff inclusion, RIP chain, and the final epoch root. The wallet fetches these automatically when you open a transfer receipt and shows every step.
  • Deposits (VTXO mints): mint transactions have no inputs, so ledger proofs do not exist for them by design. Their proof is the on-chain confirmation of the deposit transaction itself, viewable on the block explorer. The wallet labels these receipts accordingly instead of showing empty proof rows.

Every receipt in the wallet exports as JSON: a complete, shareable record of what the daemon attested, with no invented fields.

SECURITY ARCHITECTURE

Zero Key Persistence Policy

Protecting Bitcoin private keys against browser exploits, persistent malware, and cross-site scripting.

Nothing Secret Is Stored

The 12-word recovery mnemonic and derived private keys are never written to disk, localStorage, or IndexedDB. They exist only while you are using the wallet and are cleared the moment the tab closes.

What this means when you close and reopen the wallet

Because keys are never persisted, closing the tab or restarting the browser clears them. On reopen, the wallet shows a lock screen: your vault records are still on this device, and entering your 12-word phrase restores your balances, VTXOs, and proofs. There is no key file an attacker could steal from this device: only your phrase can unlock the wallet.

  • On reopen: lock screen asks for the recovery phrase; unlocking restores the full wallet.
  • Phrase lost? "Start over on this device" resets the vault records so you can create or recover a wallet. Funds in a wallet whose phrase is truly lost cannot be recovered by anyone.
  • Storage only holds public data: vault metadata, receipts, and proofs. Nothing secret is ever in it.

CUSTODY LIFECYCLE

VTXO Coin Selection & Reservation Locks

How RIPCORD selects inputs, isolates change outputs, and prevents concurrent double-spends.

  • Greedy Largest-First Selection: Deterministically picks spendable VTXOs largest-first to cover the amount plus fee, skipping spent, locked, or locally reserved inputs.
  • Local Spend Reservation: Temporarily locks selected inputs while a payment is in flight to prevent concurrent payments from double-spending the same note.
  • Single-Writer Queue: Serializes outbound payments to enforce strict state nonce progression.
  • Change Output Isolation: Change returns strictly to the sender's own user key descriptor, never into the shared validator pool.

END-TO-END WALKTHROUGH

The Complete Custody Lifecycle (Steps 01 to 06)

The complete path of Bitcoin through the RIPCORD system, from fresh mnemonic generation to off-chain transfers and disaster recovery.

01

Ephemeral Key Generation & Identity Derivation

User generates a standard 128-bit BIP-39 mnemonic (12 words). Ripcord derives root keys in RAM at path m/84'/1'/0'/0/index (BIP-84 scheme, regtest coin type 1').

02

Quorum Discovery & Vault Compilation

Ripcord queries the live Tachi daemon, validates the 5-of-7 threshold, sorts validator public keys, and derives the Taproot vault address.

03

On-Chain Deposit & Two-Step Funding

User deposits BTC into the vault address (for example from the Tachi faucet). After the deposit confirms on L1 (~10 minutes on regtest), the user taps "Check and register deposit" in the wallet: this second step is what mints the spendable VTXO. Until registration, the balance shows under on-chain vaults, not spendable sats.

04

VTXO Coin Selection & Off-Chain Transacting

Deposited BTC becomes spendable Virtual UTXOs. Outbound transfers serialize through single-writer queues with isolated change routing.

05

Live Activity Indexing & Proof Commitment

Transactions broadcast to Tachi and stream via WebSocket. Status updates in real-time as HAT and RIP proofs are anchored into rollup blocks.

06

Cold-Start Disaster Recovery

If storage is wiped completely, Ripcord restores full state using only the 12-word phrase by scanning candidate CSV blocks (2, 144, 432, 1008, 2016).

SOVEREIGNTY GUARANTEED

Unilateral Ripcord Exit

The hallmark of non-custodial custody is the ability to withdraw funds without third-party permission.

If Tachi validators disappear, experience downtime, or attempt censorship, the user pulls the Ripcord. This executes a sweep transaction on Bitcoin L1 using the user's sovereign private key after the BIP68 relative timelock has elapsed.

SOVEREIGN EXIT

BIP68 Relative Timelocks (CSV)

The unilateral exit path uses OP_CHECKSEQUENCEVERIFY starting from the confirmation block height of the funding outpoint.

Exit Lifecycle Status Timelock Condition User Action Permitted
unfunded No on-chain funding outpoint detected Fund vault on L1 before testing exit
maturing confirmations < csvBlocks Dry-run test-pull permitted; broadcast locked
live confirmations ≥ csvBlocks Full unilateral exit ready: User CHECKSIG can sweep to L1
spent Funding outpoint has been spent on L1 Funds already swept or settled

SOVEREIGN EXIT

Dry-Run Test-Pull Engine

Eliminate user uncertainty before executing an on-chain broadcast through simulated witness construction.

  • Builds the exact Bitcoin L1 witness transaction.
  • Signs the Tapscript leaf with the user's own key locally (the exact final witness), so the reported vsize is the real spend size.
  • Computes virtual size (vsize) and sequence number (nSequence = csvBlocks).
  • Computes the deterministic transaction hash (txid) without broadcasting anything.

Hold-to-Confirm Physical Mechanism

Broadcasting an exit on L1 incurs standard Bitcoin mining fees and closes the off-chain vault. RIPCORD protects users from accidental triggers with a 1.2-second hold-to-confirm physical button.

VAULT MONITORING

Sentinel Vault Health

A watch-only health score for your vault. Sentinel reads the network and your vault's state, explains both in plain English, and signs nothing. It lives on the Wallet tab and never moves a satoshi.

What it checks

  • Watchtower receipts: on-chain activity against your vault, classified as legitimate or a breach.
  • Exit maturity: how far the exit timelock has matured, with a plain-English countdown.
  • Balance cross-check: your vault record's numbers against the live chain snapshot.
  • Quorum health: how many validators are live versus the 5-of-7 threshold.
  • Watchtower liveness: whether the surveillance scan is keeping up with the chain.

How it reads

A single 0 to 100 score, a one-line summary, and a findings list where every item names the fact behind it. When the daemon cannot be reached, Sentinel says "paused" and refuses to score what it cannot see. Alerts (browser notifications when permitted) fire once per finding, and the raw watchtower audit sits behind a "Surveillance details" drawer in the same panel.

Evidence: 20 engine tests in packages/core/test/sentinel.test.ts. The engine is pure data in, data out, and never throws.

SOVEREIGNTY, PROVEN

Exit Readiness Certificate

The exit is not a promise in a document. The wallet proves it and hands you the evidence. The certificate sits on the Exit tab and exports as JSON for anyone to re-verify.

The four checks

  • Timelock: the CSV committed inside the exit script equals the vault's declared timelock and cannot be shortened.
  • Your key: the exit leaf commits the key derived from your own recovery phrase, not whatever a stored record claims.
  • Script shape: the exit script is exactly the sovereign shape: wait, drop, your key, check signature.
  • Tree proof: the stored exit leaf and BIP-341 control block re-derive exactly to your on-chain address. This is verified on this device with no exit dry run needed, and it passes even for a vault whose funding is already spent.

Honest by construction

A missing script fails its checks; nothing is synthesized to make the card look good. A vault whose funding is already spent discovers the spending transaction from the node: when it is a verified sovereign sweep to your own L1 address, the certificate reports the exit transaction, its amounts, and its confirmations; when it is not, it says there is nothing left to exit instead of claiming enforcement. The exported JSON carries the raw public evidence: the full public key, the exit leaf in hex and script form, the leaf hash, the control block, the taproot output key, the funding outpoint, and the node-verified sweep evidence (exit transaction id and raw hex, destination, amount, fee, block hash, confirmations, and the explorer link). A sweep is only labelled a sovereign exit when the funding outpoint is its sole input and every output pays your L1 address, and only counts as done once it has at least one confirmation.

Evidence: 16 tests in packages/core/test/exit-certificate.test.ts (including hex disassembly of the real vault leaf and negative-script cases), 18 in exit-certificate-sweep.test.ts, and 5 live read-only checks across 3 tests in exit-spender-live.test.ts that verify the sweep evidence against the real daemon.

BEFORE THE MONEY MOVES

Spend Conscience & Fee Transparency

Your own rules, checked before every send, and a fee you actually choose. Both are quiet by default: until you switch rules on, sending behaves exactly as it always did.

Spend Conscience

  • Per-send limit and a rolling 24-hour limit, both your numbers.
  • New recipient warning when an address is not one you have used or saved before.
  • Large share warning when a send is a big slice of your spendable balance (threshold is yours).

When a rule flags a send, a sheet shows every rule with its real numbers and offers "Looks right, send" or "Cancel". The rules never block on their own: the decision stays yours, but a bad send has to get past your own rules first.

Fee transparency

The fee row is a real choice: Slow, Normal, and Fast presets from the daemon's live estimates, plus a custom fee you type. The fee you pick is the fee the send uses, and the review labels its timing estimate as an estimate.

Evidence: 13 tests in packages/core/test/spend-conscience.test.ts, including boundary cases and the exact large-share comparison.

DISASTER RECOVERY

Cold-Start Disaster Storage Wipe Recovery

Complete state restoration from only the 12-word recovery phrase with zero centralized servers.

There are two levels of restore, and both need only your 12-word phrase:

  • Everyday unlock (page reopened, storage intact): the wallet shows its lock screen; entering the phrase restores your keys on the spot and your balances, VTXOs, and receipts return immediately.
  • Cold-start (storage wiped completely): if browser storage is cleared entirely (IndexedDB, cache, localStorage), the "Recover wallet" flow scans candidate CSV blocks (2, 144, 432, 1008, 2016), binds to live Bitcoin RPC funding scripts, reconnects to the indexer, and reconstructs the wallet with zero central dependencies.

SECURITY GUARANTEES

Non-Negotiable Protocol Invariants

Five foundational rules enforced across both the SDK and wallet UI to guarantee fund security.

1. Ephemeral Signing
BIP-39 mnemonic seeds and private keys are never written to storage. Only public metadata is stored in IndexedDB.
2. Change Isolation
Payment change always returns to the sender's own user key descriptor, never into the shared vault pool script.
3. Zero Mocks
Every balance, confirmation, proof check, and exit assessment is executed against live Tachi regtest and Bitcoin RPC outputs.
4. Script Binding
Funding outputs are verified against Bitcoin RPC via exact scriptPubKey matching. No unverified deposit is reported as confirmed.
5. Scope Transparency
RIPCORD targets OP_FREEDOM Bounty #1 on Tachi regtest. There are no false claims of mainnet support; regtest is a deliberate, honest verification boundary.

SatVM Smart Contracts on TAURUS

Forward-compatible smart contract architecture for Turing-complete state transitions directly against Virtual UTXOs (VTXOs) via SatVM covenants targeted for Phase 2 ecosystem grant expansion.
